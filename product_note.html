1. Vision & Problem Statement

The vision: a personal, always-running utility that continuously watches a whitelist of Indian listed companies — starting with a handful and growing over time — extracts structured meaning from everything they disclose, and surfaces ranked, explainable invest / disinvest signals where the user actually looks: Telegram.

The problem it solves. Meaningful information about Indian companies arrives scattered across exchange announcement feeds (thousands of PDFs weekly), news portals, and aggregators. No retail-friendly tool reliably does all four of the following in one place:

  • Captures every corporate filing and news item for a tracked set of stocks, continuously;
  • Understands them — classifying what happened, to whom, and whether it matters;
  • Ranks the day's noise down to the handful of developments worth attention;
  • Delivers that digest proactively, so insight finds the user instead of the user hunting for it.
The moat is understanding, not access. Raw filings are public. The defensible value is the resolve → extract → classify → rank pipeline built on top of them. Everything in this product is organized around making that pipeline excellent.

Product identity in one sentence

A research analyst that never sleeps: it watches every disclosure and news item for the stocks you care about, and each morning hands you a short, ranked, evidence-linked briefing of what changed — plus an immediate ping when something serious breaks.

Whitelist-first, not universe-first

The tracked set is a database table, not a constant. It starts at ~10–25 stocks the owner actually follows and grows toward ~500 as the pipeline proves itself. This is a deliberate design choice with three consequences that shape the whole system:

  • Enrichment cost scales with the whitelist, not the market. Feeds are market-wide; LLM spend and PDF downloads are whitelist-gated. Adding stock #26 costs pennies, not a re-architecture.
  • Document metadata is captured for every listed company from day one, regardless of whitelist. It is ~1 MB/day and it means adding a stock later gives instant history back to the ingestion start date. Only PDF download and LLM enrichment are gated.
  • Quality is measured on a set small enough to hand-audit. With 20 stocks, the owner can verify 100% of a day's output. That validation loop is what earns the right to scale to 500.

There is exactly one user today: the owner — an engaged retail investor who makes his own buy/sell decisions and wants an edge from systematic coverage he cannot do manually.

Cadence: continuous ingestion, scheduled thinking

The old framing of this note ("daily-cadence system") was wrong and has been replaced. The correct model is three distinct clocks:

ClockCadenceWhy
Ingestion (fetch → store → resolve)Continuous, always-on. Main announcement feeds every 5 min; category feeds every 15 min; news feeds hourly per whitelisted company.Feed retention is roughly the current calendar day (measured, §5). A once-daily poll would lose items outright. Cheap: conditional GET (ETag / If-Modified-Since) makes an unchanged poll near-free.
Red-flag path≤30 min from filing appearing in a feed to Telegram alert, for severity-5 events only.An auditor resignation is worth waking up for. This SLO is what sets the 5-minute poll interval — not the other way round.
DigestOnce daily, 07:30 IST.Reading a ranked briefing is a habit, and habits need a fixed time. Depth lives behind bot commands.
What we are explicitly not doing: competing on latency with market participants. Sub-30-minute is a ceiling for one alert class, not a system-wide design target. Nothing in the pipeline assumes second- or sub-second latency, and price data is end-of-day only.

Design-for-the-future rule

Trading and portfolio modules are out of scope but not out of mind. The architecture keeps three boundaries clean so they can be added later without rework: (a) the intelligence store is written by ingestion+enrichment only, and read by anything downstream; (b) insights are just ranked events — a future trading module consumes the same stream a human sees; (c) modules communicate through defined interfaces even when running in one process tree.

6. Ingestion & Structuring Approach

Every source flows through the same six-stage pipeline. Uniformity is deliberate: adding a source means implementing adapters for the first two stages only.

StagePurposeKey rules
1. FETCH Retrieve raw bytes/XML/HTML/PDF Per-source rate limits; conditional GET (ETag / If-Modified-Since) so unchanged polls cost nothing; retries with backoff. Save raw bytes before any parsing — a failed parse must never lose fetched data. Every artifact stamped with a SHA-256 content hash.
2. EXTRACT Turn bytes into text/tables/fields XML → field mapping · HTML → readable article text · PDF → text layer. Image-only PDFs are flagged and queued, not OCR'd, until Phase 4. Table-heavy financial PDFs get a confidence score; low confidence routes to a review queue rather than a silently wrong number.
3. RESOLVE Attach the item to a real security See §7. Output is an ISIN with a confidence tier, or the unresolved queue. Nothing proceeds downstream without a resolved ISIN.
4. NORMALIZE Map into the common schema All documents become the same shape regardless of origin: ISIN, exchange, document type, event-category hint, timestamps, source metadata, raw-store path, content hash.
5. ENRICH (whitelist-gated) Add meaning Dedup (content hash → simhash → local embedding cosine), LLM fact extraction + summary + verbatim quote, then rules-based event typing, direction, and severity (§8). Extractions cached on (content_hash, model_id, prompt_version, schema_version) — never paid for twice, but a prompt fix correctly invalidates.
6. PERSIST Land in the store Metadata → documents; enriched events → intelligence; scores and deliveries → signals. Every record traceable to its raw artifact.

Scheduling model

  • Exchange feeds: main announcement feeds every 5 min; the other category feeds every 15 min; around the clock (announcements cluster post-close and on weekends — 2,064 BSE items landed on Saturday 22 Aug 2026).
  • News: one Google News query per whitelisted company per hour, staggered evenly across the hour.
  • Prices: once daily, after 16:00 IST close.
  • Enrichment: queue-driven and continuous, with severity-5 candidates jumping the queue to meet the 30-min alert SLO.
  • Digest: 07:30 IST daily.
  • Feed-depth watchdog: every poll records item count and oldest pubDate. If the oldest item is younger than the last poll's newest item, the window has truncated and items were missed → alert. This is how we detect item caps under results-season load (§16 Q1) instead of assuming.

Replayability, not bit-identical reruns

The system guarantees two things, and deliberately does not claim a third:

  • Replayable: any past day can be fully re-processed from the bronze layer with zero re-fetching.
  • Deterministic scoring: given a fixed set of extracted facts, event typing, severity, and ranking are pure functions — same input, same digest, always.
  • Not claimed: bit-identical LLM output across runs. Models drift and get deprecated. Every event row therefore records model_id and prompt_version, so an output can always be explained even when it can't be exactly reproduced.

Deduplication — why it's a first-class concern

The same announcement appears on both exchanges; the same news appears across outlets. Three layers, in cost order: exact content hash (majority case, free) → simhash near-duplicate fingerprinting (free) → local embedding cosine similarity for paraphrases (free, small CPU model). Dedup runs entirely before enrichment and consumes zero paid API calls, which is the whole point — cross-exchange PDF copies often differ by a few bytes, so hash-only dedup is not sufficient.

7. Identity Resolution (Whitelist ↔ Filing)

This is the highest-risk component in the system. A silent mis-attribution — an auditor resignation pinned to the wrong company — produces an insight that looks perfectly plausible and is completely wrong. It will not be caught by spot-checking output. It must be prevented by construction.

The problem: ISIN is the join key across every source, and the NSE feed supplies no identifier at all — the <title> is a company name string. Name matching alone is unsafe across Ltd / Limited / Ltd. variants, & vs and, renames, demergers, and genuine near-collisions (Bajaj Finance / Bajaj Finserv / Bajaj Holdings; the several "Kotak" entities).

Resolution ladder (first match wins, confidence recorded)

TierMethodConfidence
ABSE scripcode present in the item → direct lookup in the security master.Exact
BCross-exchange anchor: an NSE item whose PDF content hash or normalized title+date matches a BSE item inherits that item's scripcode → ISIN. BSE's scripcode is effectively used to identify NSE items.Exact
CSymbol or ISIN found in the document text (most filings state at least one — commonly scrip code + trading symbol — in the header/letterhead). Dry-run check on two RIL filing PDFs found scrip code and NSE symbol in the letterhead of both, but no ISIN string in either — Tier C should not assume ISIN presence.High
DNormalized-name exact match against the security master, after canonicalization (case, suffixes, punctuation, &/and, whitespace).High — only if the normalized name is unique in the master
ECurated alias table (hand-maintained: former names, common abbreviations, feed-specific spellings).High
FAnything else → unresolved queue.None

Hard rules

  • No fuzzy matching in the publish path. Fuzzy/embedding similarity may only propose candidates into the unresolved queue for human confirmation; it can never itself attach a filing to a stock.
  • Ambiguity fails closed. If a normalized name matches more than one security, the item is unresolved — never assigned to the "most likely" one.
  • Unresolved items are surfaced, not swallowed. A weekly Telegram line reports unresolved count; confirming one via bot writes a permanent alias-table entry, so the same name is never ambiguous twice. The system gets more accurate with use.
  • Whitelist gating happens after resolution, never before. Filtering on names before resolving would silently drop the misspellings we most need to catch.

Collision risk confirmed live, not hypothetical: a same-day dry run for RELIANCE (whitelist target: Reliance Industries Ltd) found "reliance"-substring matches across NSE, BSE, and Google News that are unrelated legal entities — Reliance Power Ltd (a different BSE scripcode entirely), several Reliance/Nippon Mutual Fund NAV declarations (Nippon Life India AMC, formerly Reliance Mutual Fund), and a news item on Reliance Entertainment Studios (Anil Ambani group, insolvency case). Name-substring matching alone would have mis-filed all four against Reliance Industries on the very first day.

Security master

Seeded from the NSE equity list and the BSE scrip master (symbol, name, ISIN, scripcode, status), refreshed weekly, versioned with effective dates so that a filing from six months ago resolves against the names in force then. Corporate name changes, symbol changes, and delistings are alias-table events, not row overwrites.

Target: ≥99% of items belonging to whitelisted stocks resolve at Tier A–C; unresolved queue drains to zero weekly; zero known mis-attributions. Mis-attribution rate is the one metric in this project with a zero target.

8. Intelligence Layer

Governing principle

The LLM produces facts, summaries, and quotes. Deterministic rules produce event type, direction, severity, and rank. The model never emits a score. This is a stricter line than v0.1 drew — previously severity was LLM-assigned while the note claimed ranking was deterministic, which meant the model was in fact the ranker.

What the LLM returns (JSON-schema constrained)

{
  "document_kind":      "insider_trading | results | order_win | governance | ...",
  "facts": {
     "amount_inr":            1200000000,
     "counterparty":          "…",
     "pledge_pct_after":      34.0,
     "holding_delta_pct":     -0.8,
     "officer_role":          "Statutory Auditor",
     "action":                "resignation",
     "effective_date":        "2026-08-21"
  },
  "summary_one_line":   "…",
  "supporting_quote":   "…verbatim from source…",
  "extraction_confidence": 0.0-1.0,
  "language":           "en"
}

No severity, no sentiment, no recommendation field exists in the schema. Missing facts are null — the model is instructed never to infer an unstated number.

Severity rules (deterministic, over extracted facts)

SevTrigger (evaluated in order)
5Auditor resignation or adverse/qualified opinion · regulatory penalty or SEBI order against the company or promoters · forensic audit ordered · insolvency filing · promoter pledge crossing 25% or rising >5pp in one disclosure
4MD/CEO/CFO exit · credit rating downgrade · promoter/insider transaction ≥0.5% of equity · order win ≥10% of revenue (Phase 4 — needs a revenue base; until then large absolute orders map to 3) · fundraise via equity dilution · material litigation
3Results filed · buyback / dividend / split / bonus · rating upgrade · order win of material absolute size · capex or capacity announcement
2Shareholding pattern change without threshold breach · analyst or media coverage corroborated by a filing on the same stock within 48h
1Board meeting intimation · trading-window closure · routine compliance certificates · uncorroborated news colour

Direction (positive / negative / neutral) is likewise derived from facts — sign of a holding delta, upgrade vs downgrade, resignation vs appointment. Where the sign is genuinely contested (buybacks, M&A, fundraising), the event is marked neutral and the facts are shown. v0.1's "default lean" priors are removed: asserting that buybacks are positive and M&A is structural was an unevidenced directional bet, and with backtesting out of scope there is no loop that would ever correct it.

Event taxonomy

Every event carries: type, direction, severity, affected ISIN(s), effective date, extracted facts, extraction confidence, resolution confidence, and source linkage.

OpenAI usage policy

  • Tiered routing: mini-tier models for bulk extraction; stronger models only for long documents (annual reports, transcripts) or extraction_confidence below threshold.
  • Hard budget breaker: a configurable monthly ceiling enforced in code — default ₹1,500/month (§16 Q5). On breach: enrichment pauses, ingestion continues, Telegram says so. Ingestion must never depend on API availability or budget.
  • Whitelist-gated spend: only whitelisted stocks' documents are ever sent to the API. Cost is a function of the whitelist, not of market volume.
  • Show-your-work rule: every insight carries a verbatim supporting quote. An insight whose quote does not contain the claimed fact is a bug, and is the single easiest thing for the owner to spot-check.

9. Insight Ranking & Telegram Delivery

Telegram is the product's face. If the digest isn't worth reading every morning, nothing else matters. The surface is a bot (not a channel) — channels cannot receive commands, and on-demand queries are half the product.

Daily digest format (target)

📋 MORNING BRIEFING · Sat 22 Aug 2026 · 07:30
24 stocks watched · 61 filings resolved · 6 ranked

🔴 HIGH (2)

1. ⬇️ ABC INDUSTRIES · sev 5 · Governance
   Statutory auditor resigned; promoter pledge now 34%.
   "…unable to obtain sufficient appropriate audit
    evidence in respect of trade receivables…"
   BSE · 21 Aug 18:42 · close 21 Aug: −7.2%
   📄 filing.pdf

2. ⬆️ XYZ CHEMICALS · sev 4 · Growth
   Won ₹1,200 cr multi-year export order; third large
   win disclosed this quarter.
   "…letter of award dated 20 August 2026…"
   NSE · 21 Aug 17:10 · close 21 Aug: +4.1%

🟡 MODERATE (4) → /moderate
🟢 ROUTINE (55) → /routine
❓ 3 items unresolved this week → /unresolved

Constraints this mock respects, which v0.1's did not: Telegram has no collapsible sections (depth is a bot command, not a tap-to-expand), messages cap at 4,096 characters (digest budget ≤3,500, auto-split beyond), and price is labelled as the day's close move — context, not attributed causation. Percentage-of-revenue framing is absent until a fundamentals source exists.

Delivery rules

  • One digest per morning at 07:30 IST: ranked entries, each with severity, one-line rationale, verbatim quote, source link, and prior-day close move.
  • Immediate red-flag alerts for severity-5 events, within 30 min of feed appearance, at any hour. This is the only sub-daily path.
  • Bot commands: /stock <name> recent events · /week week-in-review · /missed replay · /add & /remove whitelist management · /unresolved confirm identity matches · /health ingestion status.
  • Quiet discipline: top section capped at 10 items; routine items live behind a command; per-stock flood cap of 2 entries per digest.

Ranking philosophy

score = severity × category_weight × freshness_factor, plus hard rules: governance red flags always surface, duplicates collapse, single-stock floods are capped. Every term is now deterministic and inspectable (§8). Complexity gets added only when the simple model demonstrably misranks — and "demonstrably" means the owner flagged it via /wrong, which logs the case for review. Explainability beats sophistication at this stage.

10. Data Architecture Principles

Engine choice: PostgreSQL (decided). Chosen for JSONB (flexible per-source metadata), pgvector (local embeddings in the same engine), full-text search, and Python ecosystem fit. One engine covers relational, document, and vector needs.

Separation model: one database, one schema per domain. v0.1 called for separate databases per domain with "no ad-hoc joins" — that was microservice ceremony imported into a single-user batch system, and in Postgres it is actively harmful: cross-database joins require dblink/FDW, pgvector must be installed per database, and the single most common query in this product ("events for a whitelisted stock, with its sector and price move") spans three domains. Schemas preserve every boundary that matters — ownership, naming, permissions, and a clean later split via schema-level dump — at zero cost.

PostgreSQL database: market_intel
├── universe        security master, alias table, WHITELIST (with added_at/
│                   removed_at), sectors, index membership history
├── documents       filing/news metadata for ALL companies, resolution status
│                   + confidence, dedup keys, raw-artifact pointers
├── market_data     daily OHLCV for whitelisted stocks
├── intelligence    events, extracted facts, summaries, quotes, embeddings
│                   (pgvector), model_id + prompt_version per row
├── signals         computed scores, ranked insights, delivery log
└── ops             per-source cursors, poll history, feed-depth watchdog,
                    run reports, unresolved queue
                    (future: portfolio, execution)

Raw object store (filesystem, immutable, backed up)
├── raw/nse/{yyyy-mm-dd}/...      original XML/PDF exactly as fetched
├── raw/bse/{yyyy-mm-dd}/...
└── raw/news/{source}/{yyyy-mm-dd}/...

Ownership of overlapping concepts: corporate actions exist in two forms and the split is explicit — market_data holds the quantitative record used for price adjustment (ex-dates, ratios); intelligence holds the event that gets ranked and delivered. Neither is derived from the other; both point at the same source document.

Layering rules

LayerContainsRule
Bronze (raw store)Original bytes, untouchedImmutable. Never edited, only added. Enables full re-runs without re-fetching.
Silver (documents)Normalized, resolved document records — all companiesMetadata only, never blobs. Content-hash keyed. Source of truth for "what have we got".
Gold (intelligence, signals)Events, facts, summaries, embeddings, scoresFully regenerable from bronze+silver. Model or prompt upgrades re-run over silver — never re-fetch.

Storage sizing

  • Metadata, all companies: ~2,400 items/day × ~1 KB ≈ 1 MB/day. Negligible, and it is what makes retroactive whitelist additions possible.
  • PDFs, whitelist-gated: ~250 filings/stock/year × ~400 KB ≈ 100 MB per stock per year. At 25 stocks ≈ 2.5 GB/yr; at 500 stocks ≈ 50 GB/yr.
  • Backup: raw store and nightly pg_dump to a second physical disk, with a monthly off-machine copy. A backup that lives only on the ingesting machine is not a backup.

11. Platform Constraints & Non-Functional Requirements

ConstraintImplication for design
Single machine, always-onLong-running Python workers under OS process supervision (systemd on Linux, Task Scheduler/NSSM on Windows). No containers, no orchestration — v0.1's Docker Desktop + WSL2 + GPU-passthrough stack was the most fragile choice in the document for zero benefit at one user. Postgres runs natively.
Host is not yet fixed (Linux server vs Windows laptop with RTX 4050)Nothing in the current phases requires a GPU. This decision only gates Phase 4 OCR (§16 Q6), so it does not block the build.
Local models: embeddings (now), OCR (Phase 4)Embedding model is small and CPU-viable, so dedup and semantic search run anywhere with no API cost. If OCR arrives, it gets a single serialized GPU worker queue so jobs never contend for VRAM.
LLM via OpenAI APIMonthly cost breaker in code; caching keyed on content+model+prompt; tiered routing. Ingestion never depends on the API — fetch/store/resolve always succeed, enrichment lags and catches up.
Resumability & idempotencyEvery worker restartable from a cursor in ops; duplicate-safe writes keyed by content hash; a crash mid-poll loses nothing but time.
Politeness & legalityOfficial feeds only, at conditional-GET-friendly intervals well below a browsing human's bandwidth. Public data, personal use, no redistribution. Bot-protected endpoints are not routinely automated — the NSE JSON API stays a manual gap-filling tool, and no source whose terms forbid automated access is put on a schedule.
ObservabilityStructured logs per worker; per-run report (fetched/resolved/enriched/failed); alert-on-silence at 2h during market days (v0.1's 24h was far too coarse for a 5-minute poll loop); feed-depth watchdog; /health command on demand.

15. Success Criteria

Each criterion names its measurement method. A criterion that cannot be measured is not a criterion.

  1. Coverage — ≥95%, measured. Weekly, pick 2 random past days and reconcile every whitelisted stock's filings against the exchange announcement listing for those days. Report captured / total in the digest. (v0.1 asserted 95% with no denominator available, which made the number decorative.)
  2. Attribution — zero known mis-attributions. Every insight's stock is traceable to a resolution tier (§7); Tier D/E resolutions are sampled monthly by hand.
  3. Trust — quotes support claims. A 20-item monthly hand audit: does the verbatim quote contain the fact the summary asserts? Target 100%; any failure is a bug with a prompt or schema fix, not a tuning exercise.
  4. Habit. The owner opens the 07:30 briefing on most days and acts on it occasionally. The truest test, and the reason the digest stays short.
  5. Timeliness. Severity-5 alerts delivered within 30 min of feed appearance, measured from pubDate to Telegram timestamp, logged per alert.
  6. Resilience. Any worker can be killed at any moment and restart with no data loss; any past day can be fully re-processed from bronze with no re-fetching; the scoring layer is bit-identical on replay given fixed extractions.
  7. Discipline. Digest top section stays ≤10 items; duplicate rate under 2%.

17. Glossary

TermMeaning

ISINInternational Securities Identification Number — unique security ID shared across BSE/NSE; the universal join key in this system.

PledgePromoter shares pledged as loan collateral; rising pledge = rising risk signal.
