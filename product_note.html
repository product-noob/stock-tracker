1. Vision and user

The product is a personal research analyst for one engaged investor. It continuously watches a database-backed whitelist of Indian listed companies, captures official disclosures and selected news, extracts evidence, collapses related documents into business events, and delivers a short ranked Telegram briefing.

The value is understanding, not access. Public filings are abundant. The useful product is a trustworthy chain from fetched source → resolved company → verified evidence → business event → ranked insight → cautious market context.

Jobs to be done

User needProduct response
What changed across my stocks?07:30 IST ranked digest with one event-level item, evidence and source links.
Tell me when a serious governance issue breaks.Severity-5 Telegram alert targeted within 30 minutes of source appearance.
Show the evidence.Verified source quote/location plus locally retained public source content.
Why did this insight rank highly?Severity rule, red-flag hits, category, freshness score and market-attribution status.
Track or review a company.Bot commands for whitelist membership, company history and unresolved identity review.

The product surfaces research evidence. It does not provide investment advice, forecast prices, place orders, or claim that a filing caused a price move.

4. Product flow

SOURCE PARTITION
  → fetch exact response bytes
  → register fetch run + immutable raw artifact
  → parse idempotent raw items
  → normalize canonical announcement/news record
  → resolve company (and listing when known), else review
  → fetch/validate content with immutable attempt history
  → hash-deduplicate immutable PDF/HTML/text content
  → append media-specific text version
  → LLM extracts facts/summary/evidence candidate
  → code verifies evidence and classifies 0..N business-event mentions
  → cluster mentions/content into immutable event snapshot
  → deterministic severity/red-flag rules create insight
  → listing-level market reaction calculation with attribution gate
  → digest ranks event-level insights and stores exact composition
  → render notification once; retry the same payload; record every attempt

Durable hand-off rule

Each successful module transaction writes its canonical result and a PostgreSQL outbox event together. Workers consume durable idempotent jobs. A crash between a database commit and message publication therefore cannot strand a record, and redelivery cannot create a second logical result.

Replay contract

  • Exact response/content bytes are retained in immutable object storage with SHA-256 registration.
  • Parsed JSONB is a query aid, not the raw source of truth.
  • Text, model extraction, event clustering, severity and reaction calculations are versioned.
  • The system promises explainable replay from retained inputs; it does not promise identical output from a model vendor after model drift.

Dedup contract

  • Polling refetch: adapter idempotency key within one source partition.
  • Canonical source record: stable dedup scope/key, preserving multiple raw sightings.
  • Exact content: SHA-256.
  • Business event: company/time/fact-aware clustering across distinct content.
  • Paraphrase news: local similarity only if Phase-2 data proves it useful.

5. Identity and whitelist

Identity is deliberately three-level:

company     Tata Elxsi Limited
instrument Tata Elxsi equity share / ISIN
listing    NSE:TATAELXSI or BSE:500408

A company is the owner of a business event. An instrument is the affected security/share class. A listing is where price bars are observed. ISIN is a strong instrument identifier, not a universal company or venue identifier.

Resolution ladder

  1. BSE scrip code or another exact listing identifier.
  2. Cross-exchange anchor through a byte-identical filing or stable source-record match.
  3. Exact symbol, ISIN or scrip code found in source content.
  4. Unique normalized company-name match.
  5. Curated alias match.
  6. Manual owner decision.

Hard rules

  • No fuzzy/embedding assignment in the publish path; similarity can only suggest review candidates.
  • Ambiguous aliases may belong to multiple companies and therefore fail closed.
  • Every decision is immutable history; a correction supersedes rather than edits it.
  • The normalized company fast path is set once in the same transaction as the accepted resolution.
  • Whitelist gating occurs after identity resolution. The security master and whitelist are different tables.

6. Evidence and events

The model extracts. Code verifies and decides. The model never assigns severity, ranking, investment direction or causal market attribution.

Extraction output

{
  "document_kind": "investor_presentation",
  "summary": "Revenue grew 14.5% YoY ...",
  "facts": { "revenue": 10211000000, "growth_pct": 14.5 },
  "supporting_quote": "...exact candidate evidence..."
}

The stored execution also includes exact text-version ID, model/revision, prompt/output-schema/verifier versions, input truncation, usage and cost. Self-reported model confidence is not stored or used.

Evidence gate

  1. Normalize source and candidate quote for whitespace and extraction hyphenation.
  2. Require source containment and, where available, retain page/character location.
  3. Retry once with an exact-copy instruction when policy allows.
  4. If verification still fails, suppress the quote and block or downgrade shipping under deterministic policy.

Document kind is not event kind

A results statement, auditor report, investor presentation and press release are different document kinds that can all support one financial_results business event. Conversely, a combined filing can yield several event mentions such as AGM plus dividend plus record-date implications.

Event snapshot

An event cluster records company, affected instruments, type, direction, timing, exact evidence membership, cluster algorithm/version/confidence and input fingerprint. A correction appends a new event version. Insights reference the immutable snapshot they used.

Severity

SeverityRepresentative deterministic triggers
5Auditor resignation/adverse opinion, severe regulatory order, forensic audit, insolvency, material pledge threshold.
4MD/CEO/CFO exit, rating downgrade, material litigation/fundraise, sufficiently material insider transaction.
3Results, dividend/buyback/split/bonus, material order/capex, rating upgrade.
2Non-threshold ownership change, moderate legal/tax notice, corroborated lower-impact development.
1Routine board/trading-window/compliance item or uncorroborated news colour.

A red-flag ruleset scans structured facts and evidence text independently of category labels. Each insight stores severity basis, rulepack version, input fingerprint and exact patterns that fired.

7. Market reaction

Market context is an active, versioned event-study calculation—not a loose company/date join.

  • Bars belong to a specific listing and price series.
  • A series fixes provider symbol, interval, adjustment mode and adjustment version.
  • Provider corrections append observations; calculations retain exact bar IDs.
  • After-close/weekend/holiday events map to the next valid reaction session.
  • The baseline uses only pre-reaction data; no future observations leak into a score.
  • Where available, benchmark/sector movement is removed using an explicitly retained benchmark series and exact comparison bars.
  • A comparable unexplained anomaly lowers attribution safety.

Stored output includes event cutoff, reaction date, before/reaction bars, baseline window/session count, return and volume z-scores, benchmark/abnormal return, method version, attribution status and reason.

Language rule: “the stock fell after the filing on abnormal volume” is permitted when supported. “The filing caused the fall” is not. A database value of safe means configured gates passed, not that causality was proven.

8. Ranking and Telegram

Digest-time ranking is:

severity × category_weight × freshness_factor

Governance overrides, event deduplication, per-company caps and evidence eligibility are hard rules. Freshness and final score are stored on the digest item because they depend on the digest's coverage window; they are not permanent attributes of an insight.

Delivery rules

  • One normal 07:30 owner digest, top section capped at ten event-level insights.
  • Routine and moderate depth lives behind bot commands.
  • Severity-5 official events can create immediate red-flag notifications.
  • Each digest stores coverage window, audience, template/rulepack and exact ranked composition.
  • A notification stores the exact rendered payload and hash.
  • Retries resend that payload and record each provider attempt/message ID.
  • Reruns/superseded digests are legal; date alone is not a global uniqueness key.

9. Data and reliability principles

PostgreSQL
├── core          companies, instruments, listings, aliases, whitelist, sources
├── platform      durable jobs and transactional outbox
├── ingestion     source partitions, fetch/artifact/item lineage, normalized records
├── documents     fetch attempts, immutable content objects, text versions
├── intelligence  extraction, mentions, event versions, insights, reactions
├── market        listing-level immutable price series observations
└── delivery      digest composition, rendered notifications, send attempts

Immutable object store
└── exact feed/API/PDF/HTML/text bytes addressed and verified by SHA-256

Mutation policy

Evidence and derived snapshots reject update/delete at database level. Coordination state—jobs, cursors, running fetches and delivery workflow—is mutable, while payload/identity fields remain guarded. Corrections append superseding resolution/event/calculation rows. The normalized-record company field is a controlled cache: deferred triggers require it to match the explicit current identity assignment, including audited corrections.

Completeness policy

Every independently polled feed/symbol/query is a source partition with its own checkpoint. Polls overlap and writes are idempotent. Fetch/stage lineage and source-window telemetry diagnose gaps. Completeness is finally measured through exchange reconciliation samples; the product never equates an advanced cursor with proof of full coverage.

Migration policy

No database exists yet, so db/schema.sql is the single editable solution-design baseline and no migration folder/ledger is maintained. When the first persistent/shared database is created, its baseline will be frozen and migrations introduced from that point onward. Prompt, output schema, verifier, classifier, cluster, severity, adjustment and reaction behavior versions remain data lineage, not Git archaeology.

13. Success criteria

  1. Coverage: ≥95% on weekly sampled NSE/BSE reconciliation with explicit denominator.
  2. Attribution: zero known company/listing mis-attributions.
  3. Trust: 100% of sampled shipped evidence contains/supports the stated fact; failures are bugs.
  4. Event quality: known multi-document fixtures collapse correctly; duplicate digest items <2%.
  5. Reaction integrity: exact fixture reproduction with no future data in baselines and explicit unsafe outcomes.
  6. Resilience: forced worker termination at every boundary strands no work and creates no duplicate logical output.
  7. Timeliness: eligible severity-5 alerts delivered within 30 minutes, measured source-to-provider.
  8. Habit: top digest ≤10 items and useful enough that the owner reads it most days.
